# ADR-0009: Logging — Single Point of Logging at the Handler Layer

## Status

Accepted

## Context

Errors are wrapped progressively as they propagate up through repository
and service layers (see the project's error-wrapping convention), which
means the same underlying error is visible — with increasing context — at
every layer it passes through. Without an explicit rule, it's tempting to
log at each of those layers too, which would produce multiple log entries
for a single failure and make correlating them harder. Separately, not
every error reaching the handler represents a system problem: some are
expected outcomes of business rules (a duplicate email, an invalid value
object, wrong credentials) triggered by ordinary client input, while others
are genuinely unexpected (a lost database connection, a nil dereference).
The logging strategy needs to draw that line explicitly, not leave it to
each handler's judgment case by case.

## Decision

Logging happens in exactly one place per request: the handler layer, and
only for errors the handler does not recognize as an expected domain
outcome.

The handler already inspects errors with `errors.Is`/`errors.As` to map
them to HTTP status codes (duplicate record → 409, validation failure →
422, authentication failure → 401, and so on). Any error that matches a
known domain error is mapped to its status code and is not logged — it's
an expected result of client input, not a system fault, and logging it as
an error would bury genuinely actionable signal in noise. Any error that
falls through to the default case — one the handler does not recognize —
is logged via the request-scoped logger before responding with a generic
500, since by definition it's something unanticipated that needs
investigation.

Repository and service layers never log. They only wrap errors with
operation context so that, if the error is ultimately logged, the log line
carries enough detail to trace where it originated.

Uncontrolled panics are the one exception to "the handler decides": those
are always unexpected by definition and are caught and logged by the
recovery middleware, outside the handler's own error-handling path.

## Rationale

Concentrating logging in one place avoids duplicate log entries for the
same failure and keeps the question "where do I add a log line for this
error?" from having more than one right answer. Piggybacking the logging
decision on the same `errors.As` switch the handler already uses to choose
an HTTP status code means no separate mechanism is needed — recognized
domain errors and their logging treatment are decided together, in one
place, by the same code. Treating expected business errors as
non-loggable keeps error-level logs meaningful: a spike in ERROR entries
should mean something is actually broken, not that users are mistyping
their email during registration.

## Alternatives considered

- **Log at every layer (repository, service, handler)**: rejected —
  produces multiple log entries for a single failure, one per layer it
  passes through, making correlation harder rather than easier.
- **Log every error that reaches the handler, including expected business
  errors**: rejected — drowns actionable signal in noise generated by
  ordinary, expected client-caused failures.
- **A dedicated logging wrapper/helper invoked from multiple layers**:
  rejected as unnecessary — the existing `errors.As` dispatch in the
  handler is already the natural decision point; adding a separate
  mechanism duplicates it without benefit.

## Consequences

- (+) One log entry per failure, at the layer that already owns mapping
  errors to a response.
- (+) High signal-to-noise ratio: ERROR-level logs correspond to genuinely
  unexpected conditions, not routine validation failures.
- (+) No additional logging mechanism to maintain — reuses the handler's
  existing error-dispatch logic.
- (−) Relies on every handler's default case actually logging before
  responding; a handler that forgets this lets an unexpected error pass
  silently.
- (−) This mechanism is scoped to HTTP handlers. Any future non-HTTP entry
  point (a background job, a CLI command) will need its own equivalent
  "boundary" that owns logging the same way, since there is no handler to
  piggyback on.
